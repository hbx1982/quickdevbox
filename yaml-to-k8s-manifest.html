Kubernetes Manifests: Declarative Pod Specs, Services & Ingress Standards

Kubernetes manifests declare desired cluster state across the Kubernetes API. Manifests structure Pod specs, Deployment replicas, Service networking, and resource requests/limits following the declarative CNCF schema.

API Specification Kubernetes OpenAPI v3 / CNCF Declarative Schema
Workload Controllers Deployment, StatefulSet, DaemonSet, Job, CronJob
Networking Model ClusterIP, NodePort, LoadBalancer, and Ingress routing
Resource Enforcement requests (scheduling guarantee) vs limits (cgroup throttle/OOM)

Implementation & Code Examples

Production Kubernetes Deployment Manifest

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-service
  labels:
    app: web-service
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-service
  template:
    metadata:
      labels:
        app: web-service
    spec:
      containers:
      - name: app
        image: quickdevbox/service:1.0.0
        ports:
        - containerPort: 8080
        resources:
          requests:
            memory: "128Mi"
            cpu: "250m"
          limits:
            memory: "512Mi"
            cpu: "500m"
        readinessProbe:
          httpGet:
            path: /healthz
            port: 8080

kubectl Validation Command

# Validate manifest against cluster schema without applying

Production Infrastructure Reliability & Hardening

Managing Kubernetes Manifests configurations within automated cloud native clusters requires robust deployment practices:

  • Zero-Trust Ingress Enforcement: Protect service boundaries with strict ingress controller timeout policies, TLS termination standards, and mutual TLS (mTLS) authentication across inter-service meshes.
  • Declarative Manifest Validation: Automate schema validation and syntax linting inside CI/CD pipelines before applying infrastructure configuration units to staging and production clusters.
  • Liveness Probes & Graceful Termination: Configure proper termination grace intervals (SIGTERM traps) and decouple health check probes from heavy backend dependencies to prevent cascading reboot loops.

Frequently Asked Questions & Troubleshooting

What happens when a container exceeds its memory limit in Kubernetes?

The Linux kernel cgroup OOM (Out Of Memory) killer immediately terminates the container process with exit code 137 (SIGKILL). Kubernetes restarts the Pod and marks it with OOMKilled status.

Why should you specify both requests and limits for CPU and memory?

The scheduler uses requests to place Pods on nodes with sufficient capacity. limits prevent a runaway memory leak in one Pod from starving neighboring workloads on the same worker node.
